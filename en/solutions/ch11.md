## Solution to Exercise 01

Begin with what the row means. If each row describes an order, the identifier must distinguish orders even when several belong to the same customer or region.

The unit is one order, and `order_id` is the candidate key intended to identify it. The column name suggests its role; uniqueness and completeness must be checked in the data. The concrete construction follows in the next solution.

<a id="sol-ch11-02"></a>

## Solution to Exercise 02

This construction is open. One possible answer uses N1 and N2 in North, S1 and S2 in South, and the following values in U.S. dollars. Each dictionary describes the columns; list elements at the same position form one order. Column names and meanings remain compatible.

``` python
north_orders = pd.DataFrame(
    {
        'order_id': ['N1', 'N2'],
        'region': ['North', 'North'],
        'value': [1200, 900]
    }
)
south_orders = pd.DataFrame(
    {
        'order_id': ['S1', 'S2'],
        'region': ['South', 'South'],

print(north_orders)
print(south_orders)
```

There are two orders in each region and four distinct IDs. Other values also satisfy the prompt if they meet these conditions. Subsequent numeric results refer to this example answer.

## Solution to Exercise 03

We need to bring orders together without adding attributes of another entity. `pd.concat` receives both datasets in a list; `ignore_index=True` creates the result’s sequential index. The code also stores the expected count, interpreted in Exercise 04.

``` python
orders = pd.concat([north_orders, south_orders], ignore_index=True)
expected = len(north_orders) + len(south_orders)
print(orders)
print('Expected:', expected)
print('Actual:', len(orders))
```

``` text
  order_id region  value
0       N1  North   1200
1       N2  North    900
2       S1  South   1500
3       S2  South   1100
Expected: 4
Actual: 4
```

The `orders` dataset retains all four records and their ID–region–value associations. The first source precedes the second. Renumbering the index does not change order identifiers.

## Solution to Exercise 04

Use the count displayed in the previous solution: `len(north_orders) + len(south_orders)` adds the source counts, while `len(orders)` measures the result. We do not need to repeat the concatenation to explain the comparison.

We expected 2 + 2 = 4 rows and obtained 4. This checks the count, but does not by itself check ID uniqueness or compatibility of monetary units. Those are separate conditions.

## Solution to Exercise 05

Select `order_id`, mark repeated occurrences with `duplicated()`, and add the markers. Check the combined result: IDs that are distinct within each source could still repeat across sources.

``` python
duplicates = orders['order_id'].duplicated().sum()
print('Duplicate IDs:', duplicates)
```

``` text

```

Zero means no order appears after an earlier occurrence of the same ID. This agrees with the four supplied codes. It is not a general check of attribute integrity.

## Solution to Exercise 06

``` python
value_region = orders.groupby('region')['value'].sum()
```

## Solution to Exercise 07

## Solution to Exercise 08

Orders is the main table, with one row per order. Customers has one row per customer. The linking key is `customer_id`, which may repeat in orders. The following construction is one possible answer; C9 appears in an order but not in the reference table.

``` python
orders = pd.DataFrame(
    {
        'order_id': ['P1', 'P2', 'P3', 'P4'],
        'customer_id': ['C1', 'C2', 'C1', 'C9'],
        'value': [800, 1200, 600, 500]

)
customers = pd.DataFrame(
    {
        'customer_id': ['C1', 'C2'],
        'customer': ['Alpha', 'Beta'],
        'segment': ['Business', 'Retail']

)
print(orders)
print(customers)
```


C1 appears in P1 and P3, while the reference table contains only one description of C1. P4 points to C9, allowing us to investigate a missing match without leaving the order key empty. Dollar values are illustrative choices, not requirements of the prompt.

## Solution to Exercise 09

Call `merge` on `orders`, supplying `customers` on the right. `on` specifies the shared code and `left` retains the orders, including the unmatched one. Printing the table and counts lets us examine attributes and row count.

``` python
orders_customers = orders.merge(customers, on='customer_id', how='left')
print(orders_customers)
print('Before:', len(orders), 'After:', len(orders_customers))
```

``` text
  order_id customer_id  value customer   segment
0       P1          C1    800    Alpha  Business
1       P2          C2   1200     Beta    Retail
2       P3          C1    600    Alpha  Business
3       P4          C9    500      NaN       NaN
Before: 4 After: 4
```

Alpha and Beta attributes have been attached to their corresponding orders. P4 retains its USD 500 with missing customer attributes. We do not fill its name or segment by assumption.

## Solution to Exercise 10

The previous solution shows four rows before and four after. The reason is uniqueness of `customer_id` in the reference table: each order finds at most one customer row.

## Solution to Exercise 11

``` python
diagnostic = orders.merge(

    on='customer_id',
    how='left',
    indicator=True
)
print(diagnostic[diagnostic['_merge'] == 'left_only'])
```


The selected row is P4, linked to C9, with a value of USD 500. Its customer record is unavailable in this dataset. The diagnostic does not establish why it is missing or justify assigning a category.

## Solution to Exercise 12

Many orders can point to one registered customer: the relationship is many-to-one. After explaining that expectation, we can check the right key with `validate="many_to_one"`. The following code adds this check to the merge.

``` python
validated_orders_customers = orders.merge(
    customers,
    on='customer_id',
    how='left',
    validate='many_to_one'
)
print('Validated rows:', len(validated_orders_customers))
```

``` text
Validated rows: 4
```

The operation retains four rows and accepts the reference-table structure. C9 remains absent: `validate` checks cardinality, not reference-table completeness or matching for every order.

## Solution to Exercise 13

Only now do we add the product column to the original order dataset. In this possible answer, R1 and R2 are assigned to the four orders in the order shown. orders['product_id'] = ['R1', 'R2', 'R2', 'R1']

``` python
orders_customers_products = orders.merge(
```

## Solution to Exercise 19

## Solution to Exercise 20

The chosen report places suppliers in rows, material groups in columns, and order value in cells. `aggfunc="sum"` declares the totalization rule. In this sample, each observed combination of known supplier and group occurs once; `pivot()` could also reshape it. `pivot_table()` remains appropriate for expressing a totals report and allowing addition when more than one order occurs per combination. No repetitions should be invented in the current data.

``` python
nexus_table = known_suppliers.pivot_table(
    index='supplier',
    columns='material_group',
    values='value',
    aggfunc='sum',
    fill_value=0
)
print(nexus_table)
print('Overall total:', total_order_value)
print('Total with known supplier:', value_known_suppliers)
print('Unmatched value:', unmatched_value)
print('Reshaped total:', nexus_table.to_numpy().sum())
```

``` text
material_group  Automation  Component  Structural
supplier                                         
AlloyWorks            3200          0        2400
Logis Supply          2100       1800           0
TechSouth                0          0        1500
Overall total: 11900
Total with known supplier: 11000
Unmatched value: 900
Reshaped total: 11000
```

The table totals USD 11,000 and covers known suppliers only. N6’s USD 900 remains separate and reconciled with the USD 11,900 overall total. Zeros denote combinations with no observed value among this report’s categories; they do not mean F9 has been identified or its value is zero.
